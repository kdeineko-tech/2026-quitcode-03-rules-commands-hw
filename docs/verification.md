### `/analyze-error`

- Виклик: `/analyze-error materials/error-log.txt`
- Чи підставився `$ARGUMENTS`: **так** — рядок «Ціль:» у контексті агента вже

- Що агент назвав корінною причиною (файл, рядок, механізм): `runSync`
  (`app/src/sync/run.ts`) зберігає прогрес (`lastSyncedAt`) лише один раз,
  у самому кінці (`saveState` на рядку 36), **після** циклу розсилки всіх
  pending-лідів (рядки 24–30). Немає інкрементального чекпойнтингу й немає
  власного бюджету часу, узгодженого із зовнішнім лімітом планувальника
  (SIGKILL після 4×30с). Наслідок: якщо `runSync` не встигає завершитись до
  рядка 36 (через великий бек-лог + ретраї `postJson` на `HTTP 429`,
  бек-оф 300/600мс — `http.ts:39`), запис стану не відбувається, і
  наступний запуск через 5 хв повторно вважає ту саму пачку лідів pending →
  нескінченний цикл SIGKILL + повний ре-сенд, що й тривав ~9 годин
  (00:15–09:14) після того, як диск звільнили о 00:13:48. Усі
  фактичні номери рядків (`run.ts:17,18,24-30,36`, `state.ts:21`,
  `http.ts:39`) перевірено проти реального коду — збігаються.
- Чим відрізнив тригер від причини: явно назвав **тригер** — заповнення
  диска нічним backup'ом (`00:02:37`–`00:13:48`), через яке перший
  `saveState` (виклик одразу після `loadState`, до будь-якої розсилки)
  двічі падав з `ENOSPC`; і окремо — **корінну причину** (описано вище),
  з явним поясненням «якби тригер зник за хвилину — проблема все одно б
  тривала, бо...».
- Чи зупинився там, де сказано в Stop: **так** — видав лише звіт (тригер +
  корінна причина + опис сценарію тесту для `app/src/sync/run.test.ts`,
  сам тест не написано) і завершив словами «Чекаю підтвердження, перш ніж
  щось писати чи запускати». Жоден файл не змінено (сам підтвердив по
  `git status`, і зміни, які там були, — від попередніх задач A/B/C цієї
  сесії, не від цього запуску).

**Виправлення після рев'ю CodeRabbit.** CodeRabbit вказав, що звіт вище
неповний: названий механізм («відкладений `saveState`, немає
чекпойнтингу») справді реальний, але не пояснює, чому вже **перший**
успішний запуск о `00:15:00` розіслав ~400+ лідів одразу — це весь
синтетичний датасет, а не 10–13-хвилинний бек-лог, який назбирався б за
час, поки диск був повний. Перевірив особисто, прочитавши
`app/src/sync/state.ts`:

```ts
export function loadState(path: string): SyncState {
  if (!existsSync(path)) return { ...INITIAL_STATE };
  try {
    return JSON.parse(readFileSync(path, "utf8"));
  } catch {
    return { ...INITIAL_STATE };   // мовчки, без жодного логу
  }
}

export function saveState(path: string, state: SyncState): void {
  writeFileSync(path, JSON.stringify(state, null, 2));  // не атомарно
}
```

Повний, виправлений ланцюжок:

1. **Тригер** — `ENOSPC` (`00:02:37`–`00:13:48`), як і раніше.
2. **Підсилювач 1 (пропущений у першому звіті):** `saveState`'s
   `writeFileSync` не атомарний (truncate + write в один виклик). Перші
   два виклики `saveState` (`run.ts:18`, одразу після `loadState`) падають
   з `ENOSPC` **посеред** запису — і майже напевно лишають файл стану
   пошкодженим/обрізаним. Наступний `loadState` о `00:15:00` намагається
   `JSON.parse` цей пошкоджений вміст, отримує виняток і **мовчки**
   повертається до `INITIAL_STATE` (`1970-01-01`) — без жодного логу чи
   помилки. Саме це — а не просто «backlog» — пояснює, чому перший запуск
   розіслав фактично весь датасет: з `lastSyncedAt = 1970` **усі** ліди
   стають pending. Це саме той патерн, проти якого застерігає
   `conventions.md`: «тихо підставити значення за замовчуванням і
   працювати далі — не можна».
3. **Підсилювач 2 (з першого звіту, підтверджується):** `runSync` пише
   стан лише один раз, у самому кінці (`run.ts:36`), після циклу розсилки
   (`run.ts:24–30`). Величезний бек-лог (спричинений підсилювачем 1) не
   встигає обробитися до зовнішнього ліміту планувальника (SIGKILL після
   4×30с) — фінальний `saveState` не виконується, `lastSyncedAt`
   лишається на `1970`, і **той самий** повний ре-сенд повторюється кожні
   5 хв ще ~9 годин.

**Фактичний результат запуску, що підтверджує підсилювач 1** — новий тест
`app/src/sync/state.test.ts` (`loadState`/`saveState` викликано напряму,
без моків; це не запропонований, а вже написаний і зелений тест — фіксує
поточну поведінку, не змінює `state.ts`):

✓ state > мовчки повертається до початкового стану, якщо файл
  пошкоджений (не кидає)

Другий тест пише в файл стану свідомо обрізаний (пошкоджений) JSON —
відтворюючи те, що ENOSPC посеред `writeFileSync` лишає на диску — і
підтверджує: `loadState` повертається до `1970-01-01`, нічого не кидаючи.
Виправлення самого `state.ts` — за бажанням, поза межами цього завдання
