- Чим відрізнив тригер від причини (у живому запуску): явно назвав

  причина + опис сценарію тесту для `app/src/sync/run.test.ts`, сам тест не
  написано) і завершив словами «Чекаю підтвердження, перш ніж щось писати

  цього запуску).

**Виправлення після рев'ю CodeRabbit (замінює класифікацію вище, а не
доповнює її).** CodeRabbit двічі вказав на неточність: спершу — що звіт
живого запуску не пояснює, чому вже **перший** успішний запуск о `00:15:00`
розіслав ~400+ лідів одразу (весь синтетичний датасет, а не 10–13-хвилинний
бек-лог); потім — що я сам, виправляючи це, помилково назвав знайдений
механізм «підсилювачем», хоча за суттю це і є корінна причина. Перевірив
особисто, прочитавши `app/src/sync/state.ts`:

```ts
export function loadState(path: string): SyncState {
  if (!existsSync(path)) return { ...INITIAL_STATE };
  try {
    return JSON.parse(readFileSync(path, "utf8"));
  } catch {
    return { ...INITIAL_STATE };   // мовчки, без жодного логу
  }
}

export function saveState(path: string, state: SyncState): void {
  writeFileSync(path, JSON.stringify(state, null, 2));  // не атомарно
}
```

**Фінальна, авторитетна класифікація** (замінює живий висновок агента вище):

- **Тригер:** `ENOSPC` (`00:02:37`–`00:13:48`) — заповнення диска нічним
  backup'ом.
- **Корінна причина:** `loadState()` (`state.ts:11-18`) на будь-яку помилку
  `JSON.parse` **мовчки** повертається до `INITIAL_STATE` (`1970-01-01`),
  нічого не логуючи й не позначаючи як помилку. Саме це — а не просто
  «backlog» — пояснює, чому перший запуск розіслав фактично весь датасет: з
  `lastSyncedAt = 1970` **усі** ліди стають pending. Це рівно той патерн,
  проти якого застерігає `conventions.md`: «тихо підставити значення за
  замовчуванням і працювати далі — не можна» — тут те саме стається не в
  інтеграції, а в самому `sync/state.ts`.
- **Підсилювачі:**
  1. `saveState()`'s `writeFileSync` не атомарний (truncate + write в один
     виклик) — перші два виклики (`run.ts:18`, одразу після `loadState`)
     падають з `ENOSPC` **посеред** запису й майже напевно лишають файл
     стану пошкодженим — це і є те, що потім змушує `loadState` піти в
     `catch`-гілку й спрацювати корінній причині.
  2. `runSync` пише стан лише один раз, у самому кінці (`run.ts:36`), після
     циклу розсилки (`run.ts:24–30`). Величезний бек-лог (спричинений
     корінною причиною) не встигає обробитися до зовнішнього ліміту
     планувальника (SIGKILL після 4×30с) — фінальний `saveState` не
     виконується, `lastSyncedAt` лишається на `1970`, і **той самий** повний
     ре-сенд повторюється кожні 5 хв ще ~9 годин (00:15–09:14).

**Фактичний результат запуску, що підтверджує корінну причину** — новий тест
`app/src/sync/state.test.ts` (`loadState`/`saveState` викликано напряму,
без моків; це не запропонований, а вже написаний і зелений тест — фіксує
поточну поведінку, не змінює `state.ts`):

```

✓ state > мовчки повертається до початкового стану, якщо файл
  пошкоджений (не кидає)
✓ state > зберігає і читає стан через повний цикл

     Tests  3 passed (3)
```

Другий тест пише в файл стану свідомо обрізаний (пошкоджений) JSON —
відтворюючи те, що ENOSPC посеред `writeFileSync` лишає на диску — і
підтверджує: `loadState` повертається до `1970-01-01`, нічого не кидаючи.
Виправлення самого `state.ts` — за бажанням, поза межами цього завдання
